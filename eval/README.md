# The eval harness (SPEC.md §21, §25 Day 5)

§25's Day 5 row, verbatim:

> Eval harness: fixture format, snapshot sanitiser, frozen snapshots,
> eval/run.ts, metrics, markdown report, dev/holdout split. **Kushagra labels 60
> fixtures.**
>
> Exit criteria: Eval runs offline in under two minutes; no real address in the
> committed corpus; baseline recorded.

This directory is the harness. **It is not the milestone.** Day 5 is exited when
a person has labelled sixty real fixtures *and* a baseline has been measured
over them — and the baseline needs a Day 6 predictor, which does not exist. Both
of those are stated again at the bottom, because the tooling will tell you the
same thing every time you run it.

Day 6's work — the rubric, `practice_area_priors`, the grounding filter, the
thresholds, the provider bake-off — is **out of scope here**, and nothing in
this directory invents a number that belongs to it.

---

## What a fixture is

One company. One registrable domain (§4's `canonical_domain`). The pages §10
stage 3 fetched for it, each carrying:

* the final URL, HTTP status and robots decision;
* the **sanitised page text** the fetcher stored — never raw HTML, because §8
  keeps markup out of the database and a fixture is not a loophole;
* the snapshot's own `content_hash`, plus a sha256 of the text;
* the deterministic Tier A scan (§9), with `unknown` kept distinct from `absent`.

Plus a `fixture_id` derived from the set and the domain, and a `content_digest`
over the pages. That digest is checked on every read: a hand-edited fixture is
refused, because a corpus that can be edited quietly is not ground truth.

**A fixture carries no timestamps and no database ids** — no row uuid, no trace
id, no `created_at`, and no freeze time either. Its identity is its content, so
re-freezing unchanged evidence produces byte-identical output and a `git diff`
means something. Every file is canonical JSON: keys sorted, two-space indent,
one trailing newline.

A fixture never needs a network fetch to replay. That is the whole point.

```text
eval/fixtures/<fixture-set>/
  companies/<domain>.json   one frozen fixture — immutable evidence
  labels.json               the human's decisions, with who and when
  split.json                dev or holdout per domain — checked in
```

Three files because they have three lifetimes. A fixture must not change when
someone labels it; a label must not change when the split is rebuilt.

## Freezing

```bash
EVAL_SOURCE_DATABASE_URL=<operator_ro url> \
  npm run eval:freeze -- --fixture-set=au-criminal-defence-60 \
    --domains=firm-a.com.au,firm-b.com.au

# or from a file: one domain per line, # comments ignored
  npm run eval:freeze -- --fixture-set=au-criminal-defence-60 \
    --domains-file=./ops/day5-corpus/domains.txt
```

* **Read-only.** The one statement is a `SELECT`; point the URL at
  `operator_ro` and §17's privilege model enforces it too.
* **No fetch, no model, no provider.** A fixture is made of evidence the
  pipeline already has.
* **Selection is always explicit.** There is no `--all`: a corpus assembled from
  "whatever was in the table that afternoon" is not reproducible.
* **Overwrite is refused** unless `--replace` is passed. `--dry-run` shows what
  would happen.

Production currently holds about 26 companies, not 60. The harness works for
whatever is there; reaching sixty means freezing more source material first.

## Labelling — this part is a human's

```bash
# look at the evidence for the next unlabelled fixture
npm run eval:label -- --fixture-set=au-criminal-defence-60 --next

# or one in particular
npm run eval:label -- --fixture-set=au-criminal-defence-60 --show=firm-a.com.au

# then record the decision
npm run eval:label -- --fixture-set=au-criminal-defence-60 \
  --domain=firm-a.com.au --label=qualified --by="Kushagra" \
  --reasons=small_firm,no_aw_tag
```

* `--label` is `qualified` or `rejected` — §4's `eval_label`, two values. A
  *predictor* may answer `uncertain`; a human labelling ground truth may not.
* `--by` is required. An unattributable ground truth cannot be questioned later.
* `--labelled_at` is generated by the tool, not typed.
* An existing label is **never** silently replaced. `--replace` overrules a human
  decision and says whose it was.
* Nothing infers, defaults, suggests or pre-fills a label. There is no model call
  anywhere in the labelling path, and the brief it prints contains no score and
  no suggestion — a labeller nudged by a machine is no longer independent.

### Progress

```bash
npm run eval:status -- --fixture-set=au-criminal-defence-60
```

Prints fixtures, labelled, unlabelled, qualified, rejected, dev, holdout,
unassigned, who has labelled, and whether the sixty-label criterion is met. It
does not round up and it does not call 59 done.

## The dev/holdout split

The repository preserves **no authoritative ratio** — §25 says "dev/holdout" and
no number anywhere says how many of each. So none is invented: you state the
counts, and the result is written to a manifest you commit.

```bash
npm run eval:split -- --fixture-set=au-criminal-defence-60 \
  --dev-count=40 --holdout-count=20 --dry-run     # see the plan
npm run eval:split -- --fixture-set=au-criminal-defence-60 \
  --dev-count=40 --holdout-count=20               # write it
npm run eval:split -- --fixture-set=au-criminal-defence-60 --audit
```

* **Deterministic.** Unassigned domains are ordered by
  `sha256(fixture_set + "\n" + domain)`, so the assignment is identical on every
  machine and carries no information a tuner could use.
* **Complete.** The counts must account for every unassigned fixture, so each one
  lands in exactly one split.
* **Append-only.** A domain already in the manifest keeps its split. Adding
  fixtures later assigns only the new ones. Nothing moves.
* **No label leakage.** `eval/split.ts` does not import the labels file and
  cannot read it. A holdout chosen by looking at labels is not a holdout.
* Changing an assignment needs `--rebuild --yes`, which says what it destroys.

### How holdout is protected

* `eval:run --split=dev` is the normal loop and needs no flag.
* `--split=holdout` is **refused** without `--allow-holdout`.
* The runner never defaults to holdout; `--split` has no default at all.
* Every holdout report opens with a `⚠️ HOLDOUT RUN` banner naming what reading
  the numbers and then tuning would cost.

## Running an eval

```bash
npm run eval:run -- --fixture-set=au-criminal-defence-60 --split=dev \
  --predictor=<id> --rubric-version=<v> --prompt-version=extract-v1
```

**There is no real predictor yet**, and running without `--predictor` says so
rather than producing a number. §25 puts the rubric, the grounding filter and the
provider bake-off on Day 6; a heuristic shipped here and called a baseline would
measure nothing while looking like it measured something.

A Day 6 evaluator implements `EvalPredictor` in `eval/predictors/types.ts` and
registers itself in `eval/predictors/index.ts`. Nothing else changes: fixture
loading, metrics and reporting are already done. A predictor is handed one frozen
fixture and nothing else — no pool, no company id — because a predictor that
could read the database could read the label.

`test-only-scripted` exists so the suite can exercise the runner end to end. It
answers from a script, reads no evidence, needs `--allow-test-predictor`, and
puts a `⚠️ TEST-ONLY PREDICTOR` banner on every report it touches.

The runner refuses: an unlabelled fixture in the split, a holdout without the
flag, a billable predictor without `--allow-billable`, a test-only predictor
without its flag, and a fixture whose digest does not match. It fetches nothing,
resolves no provider, reads no `MODEL_PROVIDER`, and touches no `companies`,
`prospects`, `web_snapshots`, `jobs` or `llm_calls` row.

### Metrics

Counting only — no target, no pass/fail. §10: "the run is what decides, not the
argument."

total evaluated, correct, incorrect, accuracy; the confusion counts (true/false
qualified, true/false rejected, and `uncertain` against each label in its own
right); qualified and rejected precision, recall and F1; total cost and mean cost
per fixture.

Every rate is `null` — rendered as an em dash — when its denominator is zero.
Not `0.0000`: a run that predicted nothing qualified has no precision, and saying
so is different from saying zero.

`uncertain` is a legitimate §10 stage 7 verdict that matches no two-valued label.
It is never counted correct, stays out of precision denominators, and stays in
recall denominators. `eval/metrics.ts` explains why in full.

### Reports

Written to `eval/reports/<timestamp>__<set>__<split>__<predictor>.md`, and
deterministic apart from the timestamp and the persisted run id. Each one carries
the fixture set, split, fixture count, rubric and prompt versions, predictor and
model identifiers, the metric table, the confusion matrix, cost totals, every
incorrect fixture with its expected label and the predictor's reasons, and the
holdout / test-only / Day-5-not-exited banners where they apply. No secret and no
credential: nothing in the report path reads an environment variable.

### Database

`--persist` writes §4's existing `eval_fixtures`, `eval_runs` and `eval_results`,
in one transaction, and **no migration was needed**. The files stay the
reproducible source material; those rows are metadata and results.

One consequence worth knowing: `eval_fixtures.label` is `NOT NULL`, so a row can
only exist for a fixture a human has already labelled. An unlabelled fixture is a
real state of the corpus that the table cannot represent — which is exactly why
the files are the source of truth, and why nothing here invents a label to make
the schema fit.

## What is still required to exit Day 5

1. **Sixty real fixtures, labelled by a human.** Not 59. Not "enough for now".
   `eval:status` will keep saying `NOT MET` until there are sixty, and so will
   every report.
2. **A baseline measured over them with a real Day 6 predictor.** None exists;
   `eval:run` says so instead of pretending.

Day 6's rubric, scoring, thresholds and provider choice remain out of scope.
